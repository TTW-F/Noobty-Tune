# Noobty Tune M1 实现计划

## 1. 文档目标

本文件面向 `M1 原型启动` 阶段，定义首轮实现的目标、范围、任务顺序与交付标准。

`M1` 的核心不是把完整产品做出来，而是建立一个可运行的前端原型，为后续 `M2 检测验证` 打基础。

## 2. M1 目标

在 `M1` 结束时，项目应具备：

- 一个可运行的 Web 前端工程
- 一个清晰的单页入口
- 一个可点击的“开始调音”入口
- 一个可正常触发的麦克风权限流程
- 一组可承载后续音频处理与 UI 的基础模块骨架

## 3. M1 不追求的内容

M1 明确不要求：

- 完整音高检测
- 调音算法稳定性
- 完整 UI 精修
- 全量测试覆盖
- 发布级体验

这些内容属于 `M2` 及之后的阶段。

## 4. M1 范围

### In Scope

- 前端工程初始化
- 页面基础布局
- 启动调音按钮
- 麦克风权限申请
- 权限成功/失败状态展示
- 基础音频上下文初始化
- 基础目录结构与模块占位

### Out of Scope

- 正式 `AudioWorklet` 接入
- 正式 `YIN` 实现
- 自动选弦逻辑
- 稳定化策略
- 完整调音仪表

## 5. 建议技术栈

### 前端框架

建议优先：

- `React`
- `TypeScript`
- `Vite`

原因：

- 工程初始化快
- Web Audio 集成灵活
- 有利于后续模块拆分与测试

### 样式方案

建议优先：

- 原生 CSS Modules 或简单全局 CSS

当前阶段不建议：

- 过早引入复杂设计系统
- 为了样式效率引入大量额外抽象

### 测试

建议至少准备：

- `Vitest`

M1 阶段即使测试还不多，也应该把入口搭好。

## 6. 目录建议

M1 阶段建议先建立如下结构：

```text
src/
  app/
  components/
  features/tuner/
  lib/audio/
  lib/music/
  styles/
  types/
```

建议职责：

- `app/`
  页面入口与应用壳

- `components/`
  通用 UI 组件

- `features/tuner/`
  调音器业务模块

- `lib/audio/`
  麦克风与音频上下文能力

- `lib/music/`
  频率、音名、调弦配置等纯逻辑

## 7. M1 任务拆解

### 7.1 初始化项目

- 创建前端工程
- 启用 TypeScript
- 配置基础脚本

完成标准：

- 项目可启动
- 本地开发服务可运行

### 7.2 建立应用壳

- 创建首页
- 放置产品标题和一句话说明
- 放置“开始调音”按钮

完成标准：

- 页面结构与产品定位清晰

### 7.3 接入麦克风权限流程

- 添加用户点击后触发权限申请
- 展示权限成功与失败状态
- 展示等待状态

完成标准：

- 能完整经历一次权限申请流程

### 7.4 初始化音频上下文

- 创建 `AudioContext`
- 在用户手势后执行初始化
- 保留停止和清理能力

完成标准：

- 页面中已有可复用的基础音频入口

### 7.5 建立业务状态骨架

- 定义初始状态类型
- 至少覆盖：
  - `idle`
  - `requesting_permission`
  - `permission_denied`
  - `initializing_audio`
  - `listening`
  - `error`

完成标准：

- 页面状态已不是散落布尔值，而是统一模型

### 7.6 建立模块占位

- 增加 `PitchDetectionEngine` 占位接口
- 增加 `Stabilizer` 占位接口
- 增加调弦配置常量占位

完成标准：

- `M2` 可以直接在当前结构上接入核心检测逻辑

## 8. 页面最低要求

M1 页面只需满足“清楚、可用、可进入下一阶段”。

最低要求：

- 首屏有产品名称
- 有一句说明
- 有主按钮
- 有状态文案区域
- 有权限失败时的明确提示

不要求：

- 完整仪表盘
- 高保真视觉效果

## 9. 状态文案建议

M1 即可落地的文案包括：

- `点击开始调音以启用麦克风`
- `等待麦克风授权`
- `正在初始化音频`
- `已开始监听，请拨动一根弦`
- `麦克风权限被拒绝，请检查浏览器设置`
- `音频初始化失败，请刷新后重试`

## 10. M1 验收标准

满足以下条件即可认为 M1 完成：

- 本地前端工程可运行
- 页面有清晰单页入口
- 用户点击后可触发麦克风权限
- 页面能正确展示权限相关状态
- 音频上下文初始化逻辑已建立
- 代码结构能支撑 M2 接入检测原型

## 11. M1 风险

### 风险 1

- 不同浏览器对权限和音频上下文的行为不同

缓解：

- M1 就在至少两类浏览器中验证权限路径

### 风险 2

- 状态管理如果一开始过于随意，M2 很快会变乱

缓解：

- M1 就建立统一状态模型

### 风险 3

- 页面过早追求样式，影响原型推进速度

缓解：

- M1 只追求清晰，不追求精修

## 12. M1 结束后的下一步

M1 完成后，直接进入 `M2 检测验证`：

1. 接入音频帧采集
2. 接入 `YIN` 候选
3. 做自动相关法对照
4. 跑低 E 到高 E 的第一轮验证
