# Guitar Tuner Web V1 PRD

## 1. 文档目的

定义 `Noobty Tune` 第一阶段 `Web` 版产品范围，确保后续设计、开发、测试围绕同一目标推进。

本版本目标不是做“最全的调音工具”，而是做一款：

- 打开即用
- 易上手
- 识别稳定
- 可继续扩展到桌面端和 App 的 Web 吉他调音器

## 2. 产品概述

### 产品名称

- `Noobty Tune`

### 当前阶段定位

- 面向 Web 端的吉他调音器
- 优先服务普通用户和新手用户
- 通过浏览器麦克风实时检测单弦音高并给出调音反馈

### 成功定义

用户可以在打开页面后的短时间内完成以下任务：

- 理解产品是做什么的
- 愿意授权麦克风
- 成功识别拨弦音高
- 理解当前该往“拧紧”还是“拧松”调整
- 将目标弦调到可接受的准确范围

## 3. 用户与场景

### 目标用户

- 初学吉他的用户
- 临时需要调音、但不想下载 App 的用户
- 需要快速校准吉他的普通演奏者

### 核心使用场景

- 用户刚拿起吉他，想快速恢复标准调弦
- 用户在手机或电脑浏览器里临时调音
- 用户不熟悉音名和频率，希望界面直接告诉他怎么调

### 非核心场景

- 专业录音级高精度调音
- 多种乐器统一支持
- 和课程、曲库、节拍器等复杂练习功能集成

## 4. 产品目标与非目标

### 产品目标

- 提供稳定的六弦吉他标准调弦体验
- 降低新手对音名、频率、sharp/flat 的理解门槛
- 建立可复用的音高检测核心逻辑，方便后续扩展到桌面端和 App

### 非目标

- V1 不追求支持所有乐器
- V1 不追求支持大量 alternate tunings
- V1 不做账号、社区、课程、曲库
- V1 不上传音频到云端做分析

## 5. V1 范围

### In Scope

- 六弦吉他标准调弦
- 标准音：
  - `E2`
  - `A2`
  - `D3`
  - `G3`
  - `B3`
  - `E4`
- 浏览器麦克风权限申请
- 实时音高检测
- 当前目标弦展示
- 当前识别音名展示
- 偏高 / 偏低方向提示
- `cents` 偏差可视化
- 已调准状态提示
- 基础异常状态提示
- 桌面端和移动端浏览器可用

### Out of Scope

- Drop D / D Standard / Open tunings
- 尤克里里、贝斯、小提琴等其他乐器
- 多弦同时识别
- 参考音播放
- 用户登录与历史记录
- 国际化

## 6. 核心用户流程

### 主流程

1. 用户进入页面
2. 页面简洁说明产品用途与所需权限
3. 用户点击“开始调音”
4. 浏览器请求麦克风权限
5. 用户授权成功后进入调音界面
6. 用户拨动某一根弦
7. 系统识别当前音高并与目标音比较
8. 页面反馈偏差方向和偏差程度
9. 用户继续调整弦钮
10. 页面提示“已调准”或等价成功状态

### 异常流程

- 用户拒绝权限
- 浏览器不支持相关 API
- 没有检测到足够清晰的输入
- 环境噪声过大导致结果不稳定
- 设备没有可用麦克风

## 7. 功能需求

### FR-1 开始调音

- 页面必须提供明确的开始入口
- 在用户主动点击前，不自动申请麦克风权限

### FR-2 麦克风授权

- 用户点击开始后触发麦克风授权
- 若授权失败，页面必须展示可理解的失败原因与下一步建议

### FR-3 标准调弦展示

- 页面默认展示六弦标准调弦目标
- 用户能清楚看到每根弦对应的目标音名

### FR-4 实时识别

- 用户拨动单根弦后，系统应在短时间内给出检测结果
- 结果至少包含：
  - 当前音名
  - 当前频率或等价信息
  - 与目标的偏差方向
  - 与目标的偏差幅度

### FR-5 调音反馈

- 当音高低于目标时，提示用户调高
- 当音高高于目标时，提示用户调低
- 当检测结果进入可接受范围并保持稳定时，提示用户已调准

### FR-6 稳定化处理

- 页面不能把每一帧原始检测结果直接暴露给用户
- 必须对检测结果做一定程度的稳定化处理，避免界面剧烈抖动

### FR-7 异常提示

- 在无输入、输入太弱、噪声太大、权限失败等情况下，必须提供文字提示

### FR-8 响应式适配

- 页面在手机浏览器和桌面浏览器都应可用
- 主要反馈区域在小屏设备上不能拥挤到难以阅读

## 8. 非功能需求

### NFR-1 可理解性

- 新手用户在首次访问时应能快速理解页面用途
- 文案优先使用“调高/调低/已调准”这类直接表达，而不是只显示技术名词

### NFR-2 实时性

- 从用户拨弦到看到稳定反馈，延迟应尽量短
- 不能出现长时间无反馈后突然跳值的体验

### NFR-3 稳定性

- 对同一根稳定拨响的弦，反馈不能频繁在多个目标音之间跳动

### NFR-4 浏览器约束兼容

- 方案必须兼容现代主流浏览器的麦克风和 Web Audio 能力
- 部署环境必须满足安全上下文要求

### NFR-5 可扩展性

- 音高检测逻辑应尽量与 UI 分离
- 后续桌面端和 App 需要能够复用检测核心或核心算法层

## 9. 信息架构

建议 V1 仅保留单页结构：

- 顶部：产品名称和一句话说明
- 中部：开始调音 / 权限状态 / 异常状态
- 核心区域：当前目标弦、当前识别音、偏差仪表、成功状态
- 辅助区域：六根弦标准音列表、简短新手提示

## 10. 关键交互要求

### 开始前

- 要让用户知道会请求麦克风权限
- 要让用户知道不会录音上传

### 调音中

- 当前主要反馈元素必须足够醒目
- 偏差方向要一眼能看懂
- 成功状态要明显，但不能闪烁过度

### 异常时

- 不能只显示“error”
- 必须告诉用户可执行的下一步，例如：
  - 靠近麦克风
  - 单独拨一根弦
  - 降低环境噪声
  - 检查浏览器权限

## 11. 验收标准

以下条件满足时，可认为 V1 达到可用：

- 用户首次进入后能明确知道这是吉他调音器
- 用户可通过点击操作触发并完成麦克风授权
- 六弦标准调弦目标清晰可见
- 用户单独拨弦时，系统能稳定识别对应音高趋势
- 页面能正确提示偏高 / 偏低 / 已调准
- 权限失败、无输入、信号过弱等情况有明确提示
- 手机和桌面浏览器都能完成基础调音流程

## 12. 风险与待验证问题

### 产品风险

- 新手未必理解弦名和音名的关系
- 用户可能不知道应该一次只拨一根弦

### 技术风险

- 低 E 弦低频识别稳定性不够
- 不同设备麦克风质量差异大
- 主线程负载可能影响识别稳定性
- 浏览器权限和自动播放策略可能影响初始化体验

### 需要尽快验证的问题

- 哪种检测算法在浏览器端对吉他单音更稳
- `AudioWorklet` 是否有必要在第一版就接入
- UI 上应以“自动识别当前弦”为主，还是允许用户手动选择目标弦

## 13. 版本规划建议

### V1

- 六弦标准调弦
- Web 麦克风识别
- 单页调音体验

### V1.1

- 增加手动选择目标弦
- 增加参考音
- 优化稳定性和异常提示

### V2

- 支持更多调弦方式
- 支持更多乐器
- 评估桌面端与 App 复用方案
