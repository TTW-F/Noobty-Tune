# Noobty Tune Web V1 技术设计草案

## 1. 文档目标

本文件用于将 `PRD` 中定义的产品需求转化为可实现的技术方案，重点回答以下问题：

- Web 版吉他调音器的最小技术闭环是什么
- 系统应如何拆分模块
- 音频采集与音高检测应如何组织
- 哪些实现细节需要优先验证
- 如何为后续桌面端和 App 复用打基础

## 2. 设计原则

### 目标优先级

当前阶段优先级建议如下：

1. 可用性
2. 稳定性
3. 可理解性
4. 可扩展性
5. 极致性能

这意味着：

- 首版方案优先保证“能稳定调音”
- 不为尚未验证的远期能力过度设计
- 但要保留核心模块复用边界，避免未来完全推倒重来

### 技术原则

- 音频分析尽量本地完成，不上传用户音频
- 音频处理链和 UI 展示层分离
- 原始检测值不能直接驱动 UI
- 优先建立可测的纯逻辑模块
- 在满足需求前提下，先选实现复杂度更低的方案

## 3. 系统边界

### V1 系统输入

- 浏览器麦克风音频流
- 用户的开始调音操作
- 可能的手动选择目标弦操作

### V1 系统输出

- 权限状态
- 音频状态
- 当前检测到的音高
- 当前目标弦
- 偏高 / 偏低 / 已调准反馈
- 错误和提示信息

### V1 不处理的内容

- 账号与持久化
- 服务端存储
- 音频上传分析
- 复杂推荐逻辑

## 4. 总体架构

建议采用单页前端架构，分为四层：

1. `UI Layer`
- 页面组件
- 调音反馈展示
- 状态提示与交互

2. `Application Layer`
- 调音流程状态机
- 目标弦管理
- 检测结果聚合
- 业务规则判断

3. `Audio Domain Layer`
- 音频输入适配
- 音高检测算法
- 信号质量评估
- 稳定化过滤

4. `Platform Layer`
- `getUserMedia`
- `AudioContext`
- `AudioWorklet` 或分析节点
- 浏览器权限与兼容性处理

建议边界原则：

- `UI Layer` 不感知底层算法细节
- `Audio Domain Layer` 不直接操作界面
- 检测引擎的输出应是结构化结果，而不是页面专用字段

## 5. 模块拆分建议

### 5.1 Audio Input

职责：

- 申请并管理麦克风权限
- 获取用户音频流
- 初始化音频上下文
- 提供统一的音频帧输入给检测层

建议接口：

- `start()`
- `stop()`
- `getStatus()`
- `onAudioFrame()`

关注点：

- 浏览器权限状态
- 音频上下文挂起与恢复
- 多次启动/停止的一致性

### 5.2 Pitch Detection Engine

职责：

- 从输入音频帧中估算基频
- 输出候选频率、置信度和质量指标

建议输出结构：

```ts
type PitchSample = {
  frequencyHz: number | null;
  clarity: number;
  volume: number;
  timestamp: number;
};
```

实现建议：

- 第一阶段优先验证 `YIN`
- 保留切换为自动相关法或 `WASM` 实现的能力

### 5.3 Pitch Interpreter

职责：

- 将频率转换为最接近的音名
- 计算与目标弦之间的 `cents` 偏差
- 判断是偏高、偏低还是已调准

建议输出结构：

```ts
type TuningReading = {
  targetNote: string;
  detectedNote: string | null;
  frequencyHz: number | null;
  centsOffset: number | null;
  direction: "flat" | "sharp" | "in_tune" | "unknown";
  confidence: number;
};
```

### 5.4 Stabilizer

职责：

- 去除明显异常值
- 平滑短时间内抖动
- 提供“稳定命中”判断

建议策略：

- 设置最小音量门限
- 对连续样本做窗口统计
- 排除跳变过大的离群值
- 只有连续多帧满足条件时才进入 `in_tune`

### 5.5 Tuning Session State Machine

职责：

- 管理整个调音流程状态
- 为 UI 提供稳定、清晰的页面状态

建议状态：

- `idle`
- `requesting_permission`
- `permission_denied`
- `initializing_audio`
- `listening`
- `signal_weak`
- `detecting`
- `unstable`
- `in_tune`
- `error`

### 5.6 Target String Resolver

职责：

- 管理当前目标弦
- 支持自动推断或手动指定

V1 建议：

- 默认自动匹配最近的标准弦
- 保留手动指定目标弦的设计空间

原因：

- 自动识别更适合新手
- 但在相邻音之间反复跳转时，手动锁定可能是后续体验优化点

## 6. 音频链路建议

### 建议链路

1. 用户点击开始
2. 请求麦克风权限
3. 创建 `AudioContext`
4. 将 `MediaStream` 接入音频分析链路
5. 将音频帧送入检测引擎
6. 检测引擎输出频率候选
7. 稳定化模块处理候选结果
8. 解释层生成用户可理解的调音反馈
9. UI 渲染当前状态

### 实现分层建议

原型阶段可以先简单跑通：

- `getUserMedia`
- `AudioContext`
- 基础帧提取
- 算法验证

正式实现建议尽量转向：

- `AudioWorklet` 承担持续性音频处理
- 主线程负责状态管理和 UI 更新

## 7. 算法选择建议

### 候选路线 A：YIN

优点：

- 普遍被认为在准确率与速度上平衡较好
- 适合单音基频检测

缺点：

- 仍可能在弱信号、强泛音和噪声下误判
- 需要配套的置信度和稳定化处理

### 候选路线 B：自动相关法

优点：

- 实现简单
- 原型验证快

缺点：

- 在复杂音色和谐波场景下更易抖动
- 生产体验通常需要更多补偿逻辑

### 当前建议

- 原型验证可以并行测试 `YIN` 与自动相关法
- 如果 `YIN` 在低 E 至高 E 的整体表现更稳，则优先作为 V1 主方案
- 若纯 JavaScript 版本性能或稳定性不足，再评估 `WASM`

## 8. 关键计算逻辑

### 音名映射

需要把频率映射到十二平均律的最近音高，并计算 `cents` 偏差。

核心能力包括：

- 频率转 MIDI 或等价音高编号
- 音高编号转音名
- 根据目标弦计算偏差量

### 调音阈值

建议定义三个区间：

- `in_tune`
- `near_tune`
- `out_of_tune`

示例策略：

- `|centsOffset| <= 5` 视为已调准
- `5 < |centsOffset| <= 15` 视为接近
- `|centsOffset| > 15` 视为明显偏离

注：

最终阈值必须通过真实设备测试调整，不宜现在写死为产品承诺。

## 9. 状态机设计

### 页面主状态

```text
idle
  -> requesting_permission
  -> initializing_audio
  -> listening
  -> detecting
  -> unstable / signal_weak
  -> in_tune
```

异常支线：

```text
requesting_permission -> permission_denied
initializing_audio -> error
listening -> signal_weak
detecting -> unstable
```

### 状态设计原则

- 页面任何时刻都应有明确状态
- 每个状态都应能映射到具体文案和视觉反馈
- 错误状态应提供恢复路径

## 10. UI 与检测分离策略

建议不要让组件直接依赖底层原始采样结果。

更合理的结构是：

- 音频层输出原始样本
- 解释层输出结构化调音读数
- UI 只消费读数和状态

这样做的好处：

- 后续替换算法时不影响页面结构
- 更容易做单元测试
- 更适合未来多端复用

## 11. 可测试性设计

### 纯逻辑层优先可测试

以下模块建议设计成纯函数或近似纯函数：

- 频率转音名
- `cents` 偏差计算
- 目标弦匹配
- 稳定化过滤逻辑
- 调音状态判断

### 测试层次建议

1. 单元测试
- 频率与音名映射
- 偏差计算
- 稳定窗口逻辑

2. 集成测试
- 音频链路初始化
- 权限状态切换
- 页面状态切换

3. 手工验证
- 真实设备、真实拨弦
- 安静 / 噪声环境
- 桌面 / 移动浏览器

## 12. 后续多端复用策略

为了支持未来桌面端和 App，建议从一开始就把以下边界拆清楚：

### 可复用部分

- 音高检测算法层
- 音名和偏差计算逻辑
- 稳定化和状态判断规则
- 目标弦配置

### 平台相关部分

- 麦克风权限流程
- 音频输入适配
- UI 框架
- 生命周期与设备行为

建议未来形成如下目录边界：

- `core/`：检测与调音核心
- `platform/web/`：浏览器输入与页面接入
- `app/web/`：Web UI

## 13. 关键风险与缓解策略

### 风险 1：低频识别不稳

缓解：

- 低 E 弦作为重点测试对象
- 对不同算法做针对性对比
- 加强稳定窗口与置信度过滤

### 风险 2：噪声环境下误判

缓解：

- 设置输入门限
- 引入信号质量提示
- 对无效样本不更新主反馈

### 风险 3：主线程卡顿影响体验

缓解：

- 音频处理尽早迁移到 `AudioWorklet`
- 限制 UI 重绘频率
- 把重计算从组件渲染中抽离

### 风险 4：自动目标弦判断不符合用户预期

缓解：

- V1 先自动匹配最近弦
- 记录是否需要在 V1.1 增加手动锁定弦功能

## 14. 建议的实现顺序

1. 建立频率、音名、偏差计算的纯逻辑模块
2. 接通麦克风与基础音频链路
3. 验证最小可用音高检测
4. 增加稳定化与状态机
5. 接入 UI 展示
6. 做真实设备验证
7. 再决定是否引入更强底层实现

## 15. 当前待定项

- V1 是否同时提供手动选弦
- 检测层是直接上 `AudioWorklet` 还是先用更轻方案验证
- UI 是否采用单一主仪表，还是辅以六弦列表联动高亮
