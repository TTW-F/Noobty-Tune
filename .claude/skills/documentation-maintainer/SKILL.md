# Documentation Maintainer

该技能用于让 Agent 成为项目文档治理者，目标是：文档持续可读、可执行、可追踪、可演进、可交接。

## 面向 AI 使用者的执行约束（关键）

本 Skill 的直接使用者是 AI Agent，而非人类读者。执行时必须满足“可判定、可重复、可回放”。

### AI 快速执行版（TL;DR，先看这个）

当上下文很长或时间有限时，Agent 先按这 12 条硬规则执行：

1. 先对齐事实，后写文档；不清楚就标“待确认项”。
2. 先改 Canonical，再改索引/引用，不反过来。
3. 命中触发矩阵就必须更新文档，不可跳过。
4. 涉及路径变更时，必须先产出 `old -> new` 映射表。
5. 路径变更后必须批量修链，并做链接校验。
6. 常规任务优先增量校验；发布前或大迁移强制全量校验。
7. 索引表不可用时，降级全量扫描并重建索引。
8. 输出必须包含：变更清单、变更摘要、风险假设、后续建议。
9. 输出必须披露证据等级（低/中/高）与未验证项。
10. 任意单项评分 < 3 或总分 < 20，自动返工。
11. 未完成关键门禁（修链/校验/证据）不得标记完成。
12. 不得把推测写成事实，不得仅回复“已完成”。

### AI 决策清单（执行顺序）

按顺序决策，避免跑偏：

1. 任务分类：新建/更新/重构/校验/归档
2. 影响判断：是否命中触发矩阵
3. 分层落位：Audience -> Lifecycle -> Stability -> Granularity
4. 变更策略：普通变更 or 路径迁移
5. 校验策略：增量 or 全量
6. 交付格式：四块输出 + 自评块

### AI 输入契约

每次执行文档任务，Agent 至少应识别以下输入：

- 任务类型：新建 / 更新 / 重构 / 校验 / 归档
- 目标范围：涉及的目录、模块、文档类型
- 事实来源：代码、配置、脚本、现有文档、用户补充信息
- 约束条件：时间优先/质量优先、是否允许结构调整

若输入缺失，先基于现有事实给出“最小可执行版本”，并显式列出缺失项。

### AI 输出契约

Agent 的最终输出必须包含 4 个块：

1. 变更文件清单：明确列出更新了哪些路径
2. 变更摘要：每个文件改了什么、为什么改
3. 风险与假设：哪些结论基于假设，哪些仍待确认
4. 后续建议：下一步可执行动作（最多 3 条）

禁止只输出“已完成”或泛化描述。

### AI 决策顺序（固定）

1. 先做事实对齐，再写文档内容。
2. 先更新 Canonical，再更新引用页/索引页。
3. 先保证可执行性，再优化措辞与美观。
4. 先消除冲突，再补充扩展信息。

### AI 缺失信息处理

- 缺少关键事实时，不得编造结果；使用“待确认项”占位。
- 无法访问某证据时，明确写“未验证”，并给验证建议。
- 用户未指定格式时，默认采用本 Skill 模板与分层规则。

### AI 禁止行为

- 把推测写成确定结论。
- 改动文档但不说明依据来源。
- 仅改局部文本导致全局术语不一致。
- 覆盖历史记录且不保留迁移/归档痕迹。
- 发生路径变更（重命名/移动）却不批量更新引用链接。

### AI 完成判定（机器可判定）

仅当全部满足时才可标记完成：

- 至少 1 个文档文件被新增或更新（校验任务可例外，但需输出校验结果）。
- 输出中包含“变更清单 + 风险/假设”。
- 关键步骤可执行，且术语与路径引用一致。
- 若触发矩阵命中，已同步相应文档或给出拒绝更新理由。
- 若发生路径变更，已完成“引用批量更新 + 全量链接校验”并通过。

### AI 执行样例（输入 -> 决策 -> 输出）

样例 1：用户要求“新增部署说明”

- 输入识别：任务类型=新建；范围=`docs/operations/`；事实来源=部署脚本+Nginx 配置。
- 决策：先创建/更新 Canonical 操作文档，再在 `docs/README` 增加索引链接。
- 输出：给出变更文件清单、步骤验证方式、风险（如环境变量未覆盖）和后续建议。

样例 2：用户要求“整理历史文档”

- 输入识别：任务类型=重构/归档；范围=重复主题文档。
- 决策：指定 Canonical 文档，低优先级副本加“已迁移”并保留跳转链接。
- 输出：列出归档路径、冲突解决依据、未确认项（如历史行为是否仍生效）。

样例 3：用户要求“仅检查是否需要更新文档”

- 输入识别：任务类型=校验；范围=当前变更集。
- 决策：命中触发矩阵则要求更新，未命中则给出可追溯理由。
- 输出：校验结论 + 证据 + 建议更新的最小文档集合。

### AI 失败恢复策略（异常处理）

- 事实不足：停止扩写，输出“最小可执行版本 + 待确认项”。
- 证据冲突：按优先级规则采信，并在输出中记录冲突来源。
- 链接失效：先修复内部导航，再标注外链状态（可达/不可达/待验证）。
- 范围失控：回退到“先 Canonical 后引用”的最小闭环，分批提交。

### AI 输出格式模板（建议强制）

```md
## 变更文件清单
- `path/to/file-a.md`（新建/更新/归档）
- `path/to/file-b.md`（新建/更新/归档）

## 变更摘要
- `path/to/file-a.md`：改了什么，为什么改
- `path/to/file-b.md`：改了什么，为什么改

## 风险与假设
- 风险：
- 假设：
- 待确认项：

## 后续建议
- 建议 1
- 建议 2
- 建议 3
```

### AI 自评评分卡（0-5 分）

每次任务结束前，Agent 必须进行自评。单项满分 5 分，总分 25 分。

评分维度：

1. 事实一致性（0-5）
   - 0: 大量与代码/配置冲突
   - 3: 主要结论正确，少量未验证项
   - 5: 关键结论均有依据，且无明显冲突
2. 可执行性（0-5）
   - 0: 仅概念描述，无可操作步骤
   - 3: 核心步骤可执行，异常分支不完整
   - 5: 步骤、输入、输出、回滚完整可复现
3. 可追溯性（0-5）
   - 0: 无变更来源、无上下文
   - 3: 有基础变更记录，证据链不完整
   - 5: 变更理由、来源、影响范围可完整追踪
4. 结构正确性（0-5）
   - 0: 分层混乱，位置错误
   - 3: 大体合理，个别页面层级不优
   - 5: 分层、命名、引用均符合规则
5. 风险透明度（0-5）
   - 0: 不披露风险与假设
   - 3: 披露部分风险，缺少行动建议
   - 5: 风险、假设、待确认项和应对建议完整

### 自动返工阈值（强制）

- 任意单项 < 3 分：必须返工，不可标记完成。
- 总分 < 20 分：必须返工，不可标记完成。
- 连续两轮评分不达标：缩小范围为“最小可执行闭环”后重做。

### 发布前门禁（Pre-Release Docs Gate）

若任务涉及发布、部署、回滚或外部行为变化，交付前必须额外满足：

1. 操作文档包含回滚步骤。
2. 关键配置项含默认值与环境差异说明。
3. 至少一个验证路径可直接执行（命令或检查点）。
4. 风险与假设块中明确“已验证/未验证”状态。
5. 若涉及文档路径变更，必须附“旧路径 -> 新路径”映射与校验结果。

未满足门禁时，输出必须显式标注“不可发布”。

### 路径变更硬门禁（不可跳过）

当任务包含任一文档的重命名或目录迁移时，Agent 必须按以下顺序执行：

1. 先生成路径映射表：`old_path -> new_path`
2. 批量更新仓库内所有受影响链接（含索引页、README、ADR、Runbook）
3. 进行全量链接校验（至少覆盖所有 Markdown 相对链接）
4. 在最终输出中附上“已修复链接数/剩余异常数/异常清单”

若第 2-4 步任一步未完成，本次任务不得标记为完成。

### 归档优先策略（避免新旧并存）

当迁移已完成且新路径可用时，禁止在主文档目录长期保留新旧双份文件。

执行规则：

1. 新路径作为唯一 Canonical 文档路径。
2. 旧路径文件移动到备份目录（建议：`docs/_backup/<date>/`）。
3. 主目录不保留旧文件副本或旧路径占位文件（除非用户明确要求保留）。
4. 备份目录中的文件不参与主导航，不作为默认引用目标。

最小交付要求：

- 在迁移计划中记录“已归档文件清单”。
- 在最终输出中披露备份目录位置与归档数量。

### 链接索引表机制（性能优化，建议默认启用）

为避免每次都做全量范围查询，建议维护文档链接索引表：

- 推荐路径：`docs/_meta/link-index.json`
- 作用：记录文档间链接关系，支持增量校验与受影响范围定位
- 原则：索引是“辅助事实”，真实来源仍以文档文件内容为准
- 约束：`docs/_backup/` 下文件不纳入主索引，不作为默认引用目标

建议字段（最小集）：

- `path`: 文档路径
- `hash`: 文件内容哈希（用于变更检测）
- `outgoing_links`: 当前文档指向的相对链接数组
- `incoming_count`: 指向当前文档的反向引用数量
- `last_checked_at`: 最近校验时间
- `status`: `ok` / `warning` / `broken`

### 增量校验策略（默认）

常规任务中，Agent 优先执行增量校验，而非全量扫描：

1. 识别变更文档集合（新增/修改/重命名/移动）。
2. 仅重建这些文档的 `outgoing_links` 与 `hash`。
3. 按索引反查受影响的 `incoming` 邻接文档。
4. 对“变更文档 + 邻接文档”执行链接可达性检查。
5. 更新索引并输出受影响范围统计。

### 触发全量校验的条件（强制）

出现以下任一情况时，必须执行全量链接校验：

- 目录级迁移（批量重命名/移动）
- 删除或重命名入口文档（如 `README`、索引页、ADR 索引）
- 索引表缺失、损坏或可信度不足
- 发布前门禁校验
- 周期性巡检窗口（建议每周至少一次）

### 索引失效降级策略

当索引表不可用时，Agent 必须降级执行：

1. 显式声明“索引不可用，已降级为全量扫描”。
2. 先完成全量校验，后重建索引表。
3. 在最终输出中附“索引重建结果 + 风险说明”。

禁止在索引失效时仅做局部校验并标记完成。

### 资源预算建议（可选）

- 日常 PR：优先增量校验，控制在最小受影响范围。
- 里程碑/发布前：执行全量校验，忽略增量预算。
- 超大仓库：允许分批校验，但必须保证入口文档优先通过。

### 最小证据清单（Evidence Checklist）

Agent 在最终输出中应尽量给出以下证据类型（能给几项给几项）：

- 代码或配置来源路径
- 执行命令或验证步骤
- 变更前后差异摘要
- 关联任务/PR/Issue（若存在）
- 已知限制与未验证项

证据不足时必须声明“证据等级：低/中/高”。

### AI 输出末尾附加块（强制）

最终回复末尾追加：

```md
## 自评结果
- 事实一致性：X/5
- 可执行性：X/5
- 可追溯性：X/5
- 结构正确性：X/5
- 风险透明度：X/5
- 总分：X/25
- 是否达标：是/否
```

## 设计原则（工程化）

- 单一事实源：同一规则只在一个权威文档维护，其他文档仅引用。
- 文档即交付物：文档不是附属品，必须与代码一起评审和发布。
- 最小同步单元：任何行为变更都至少同步一条文档记录。
- 先结论后细节：读者 30 秒内应定位结论、风险、操作入口。
- 可审计：关键决策、变更原因、验证证据可回溯。

## 适用场景

当用户出现以下诉求时，应优先使用本技能：

- “更新/完善文档”
- “补充设计说明”
- “整理开发记录、日志、changelog”
- “写交接文档、部署说明、README”
- “同步代码和文档状态”
- “文档太乱，帮我规范一下”

## 核心职责

1. 维护文档真实度：文档内容必须与当前代码、配置、脚本行为一致。
2. 维护文档结构化：统一标题层级、章节顺序、术语命名、路径引用。
3. 维护文档连续性：记录变化原因、影响范围、验证方式、后续待办。
4. 维护文档可执行性：关键步骤可被照做，避免“只讲概念不讲操作”。
5. 维护文档可交接性：新人能在最短时间理解背景、现状、风险与下一步。
6. 维护文档版本化：确保不同阶段文档状态可识别、可回滚。
7. 维护文档责任边界：明确 Owner、Reviewer、更新时间与适用范围。

## 触发矩阵（何时必须更新文档）

出现以下任一情形时，必须触发文档更新：

1. 新增能力：新模块、新接口、新脚本、新部署流程。
2. 行为变化：参数、默认值、权限、错误码、交互路径变化。
3. 风险变化：稳定性、安全性、性能、成本或兼容性假设变化。
4. 流程变化：开发、测试、发布、回滚、值班、交接流程变化。
5. 决策变化：方案选型、约束条件、里程碑目标变化。

若本次变更“无需文档更新”，需在交付说明中写明理由。

## 推荐文档分层（多维模型）

不要只按“文档类别”做一维分类。默认采用四维分层：

1. 受众层（Audience）：给谁看
2. 生命周期层（Lifecycle）：处于哪个阶段
3. 稳定性层（Stability）：长期规范还是临时记录
4. 颗粒度层（Granularity）：总览、专题、操作步骤

### 维度 A：受众层（Audience）

- L0 入口层：所有人可读，快速建立上下文（如 `README`、`docs/README`）。
- L1 协作层：研发/设计/测试跨角色协作文档（需求边界、接口约定、术语表）。
- L2 专业层：面向具体角色（开发、运维、产品、设计）的深度文档。
- L3 审计层：面向管理、合规、交接、复盘的留痕文档。

### 维度 B：生命周期层（Lifecycle）

- Discover：背景、目标、问题定义、范围与非目标。
- Design：方案、架构、交互、取舍、风险评估。
- Build：开发约定、模块说明、调试指南、联调记录。
- Release：部署、发布、回滚、版本说明、变更公告。
- Operate：监控、告警、值班、故障排查、运行手册。
- Evolve：复盘、技术债、迁移计划、淘汰与归档。

### 维度 C：稳定性层（Stability）

- Canonical（权威层）：长期有效规则，允许低频修改，高审核门槛。
- Working（工作层）：迭代内高频更新，用于协作推进。
- Record（记录层）：事件快照，如发布记录、事故记录、决策记录。
- Archive（归档层）：不再维护但需可检索的历史文档。

### 维度 D：颗粒度层（Granularity）

- G0 导航页：只做“去哪看什么”，不承载细节。
- G1 总览页：模块级/主题级概览，给出边界和关键链接。
- G2 专题页：深入单一主题（如鉴频算法、权限策略）。
- G3 操作页：可执行步骤（命令、输入、输出、回滚）。

### 开发文档二级/三级分层示例（重点）

开发文档不应只有一个 `development` 目录，建议继续分层：

- `docs/development/00-overview/`
  - 开发总览、技术栈、术语、代码结构导航
- `docs/development/10-standards/`
  - 代码规范、分支策略、提交规范、评审规则
- `docs/development/20-workflows/`
  - 本地开发、联调流程、测试流程、发布前检查
- `docs/development/30-modules/`
  - 按模块维护：每个模块独立说明（职责、边界、依赖、入口）
- `docs/development/40-debugging/`
  - 常见问题、排障路径、日志定位、性能诊断
- `docs/development/90-appendix/`
  - 术语表、FAQ、历史兼容说明、废弃项说明

每个模块文档建议固定结构：

1. 模块目标与边界
2. 输入/输出与依赖
3. 核心流程与状态机
4. 配置项与默认值
5. 错误处理与降级策略
6. 调试与验证步骤
7. 变更记录与已知限制

### 路径与命名约定（建议）

- 目录前缀可用两位序号保证阅读顺序（`00`、`10`、`20`）。
- 文件名优先表达“动作 + 对象”，如 `debug-audio-input.md`。
- 禁止同名不同义文档；出现重名语义时必须拆分并互链。
- 每个目录必须有索引页（`README.md`），承担导航职责。

要求：目录结构清晰，跨文档引用统一，避免重复拷贝同一内容。

## 分层落地方法（如何决定文档放哪）

为避免“知道分层但不会落位”，每次新增/改动文档时使用以下判定顺序：

1. 先定受众：谁是第一读者（全员/协作方/专业角色/审计方）。
2. 再定阶段：该内容属于 Discover/Design/Build/Release/Operate/Evolve 哪一段。
3. 再定稳定性：是长期规则（Canonical）还是迭代材料（Working）。
4. 最后定颗粒度：是导航、总览、专题还是操作步骤。

结论格式建议：

`Audience-Lifecycle-Stability-Granularity`

示例：

- `L2-Build-Canonical-G2`：开发角色使用的长期专题说明。
- `L1-Design-Working-G1`：跨角色协作的迭代总览文档。
- `L3-Release-Record-G3`：发布过程的审计型操作记录。

## 放置与拆分规则（避免大杂烩）

- 单页超过 300 行且包含 3 个以上独立主题时，应拆分为“总览 + 专题”。
- 同一文档同时服务多个主要受众时，应拆分主文档并通过索引页聚合。
- 同时包含“原则”和“操作步骤”时，原则放 Canonical，步骤放 Working 或 Record。
- 同主题出现多份文档时，指定一个 Canonical，其余改为引用或归档。

## 跨层引用规则（避免重复）

- G0/G1 只做导航和摘要，不复制 G2/G3 细节内容。
- G2 允许引用 G3 操作页，不应嵌入长步骤。
- Record 文档可引用 Canonical 规则，不反向改写 Canonical。
- 任何跨目录引用都应使用稳定相对路径，并定期做死链检查。

## 冲突处理与优先级

当多个文档对同一主题结论冲突时，按以下优先级采信：

1. 最新且已评审的 Canonical
2. 最新 Record（发布记录/事故记录/决策记录）
3. Working 草案
4. Archive 历史文档

处理动作：

- 在低优先级文档中标记“已过期/已迁移”并链接权威来源。
- 冲突无法判定时，先输出“待确认项”，禁止强行统一结论。

## 文档生命周期与状态机

建议为文档增加状态字段（可放 Front Matter）：

- `draft`：草稿，仅供协作。
- `reviewing`：评审中，可能变更。
- `active`：生效中，作为当前依据。
- `deprecated`：待淘汰，附替代路径。
- `archived`：已归档，只读历史。

状态迁移必须可追踪，至少记录迁移日期、责任人、原因。

## 开发文档深层分层（模块级）

对于 `docs/development/30-modules/`，每个模块建议继续二级分层：

- `<module>/README.md`：模块总览、边界、入口、依赖图链接。
- `<module>/interfaces.md`：输入输出、协议、事件、错误码。
- `<module>/flow.md`：关键流程、状态机、时序或数据流。
- `<module>/config.md`：配置项、默认值、环境差异、安全注意。
- `<module>/debug.md`：定位路径、常见故障、诊断命令。
- `<module>/changes.md`：模块级变更与兼容性说明。

模块页拆分原则：

- “是什么”放 README。
- “怎么交互”放 interfaces/flow。
- “怎么调试”放 debug。
- “怎么变化”放 changes。

## 迁移策略（从旧结构到新结构）

在现有文档较乱时，按三步迁移：

1. 建立导航：先补 `docs/README.md`，不动正文，先让人找得到。
2. 建立权威源：识别重复主题并指定 Canonical 文档。
3. 渐进迁移：每次功能改动只迁移相关主题，避免一次性大重写。

迁移期间允许双轨，但必须在旧文档顶部标注迁移状态和目标链接。

## 治理指标（可度量）

建议按月统计以下指标：

- 文档覆盖率：发生行为变化的 PR 中，包含文档更新的比例。
- 一致性缺陷数：评审中发现“代码与文档不一致”的次数。
- 导航命中率：从入口页 3 次点击内找到目标文档的比例。
- 死链数量：内部链接失效总数。
- 过期文档比：`deprecated` 与 `archived` 未标注比例。

指标不是为了考核写作，而是为了发现信息架构问题。

## 治理角色与职责（RACI）

建议为文档治理定义最小角色：

- Maintainer（负责执行）：文档起草、更新、迁移、索引维护。
- Owner（最终负责）：确认业务/技术准确性，批准 Canonical 更新。
- Reviewer（评审把关）：检查结构、可执行性、一致性与引用正确性。
- Consumer（使用者）：反馈可读性、可检索性、可操作性问题。

RACI 建议：

- Canonical：Owner = A，Maintainer = R，Reviewer = C，Consumer = I
- Working：Maintainer = R，Reviewer = C，Owner = A（必要时）
- Record：Maintainer = R，Owner = A，Reviewer = C
- Archive：Maintainer = R，Owner = A，Reviewer = I

## 响应等级与 SLA（建议）

根据变更影响范围定义文档响应等级：

- P0（阻断级）：影响发布/回滚/安全，需当日更新并优先评审。
- P1（高优先）：影响开发协作或主要功能理解，建议 24h 内更新。
- P2（常规）：一般优化与补充，建议迭代内完成。
- P3（低优先）：风格优化、轻微补充，纳入文档清理批次。

建议评审 SLA：

- Canonical 文档：至少 1 名 Reviewer，必要时 Owner 双审。
- Working 文档：可单审，但涉及外部行为变化时升级为双审。
- Record 文档：发布或事故类记录应在事件结束后 24h 内补齐。

## 变更响应流程（标准化）

1. 识别影响：判断本次变更对应的文档响应等级（P0-P3）。
2. 确认权威源：定位 Canonical 文档，避免多源更新。
3. 执行更新：先改权威源，再改索引与引用。
4. 评审验收：按对应 SLA 完成结构与事实校验。
5. 回写记录：在 changelog 或记录层文档写入追踪信息。

若代码已合并但文档缺失，应触发“文档补债任务”并标注优先级。

## 周/月巡检 Playbook（可直接执行）

### 每周巡检（30-60 分钟）

- 检查本周高影响 PR 是否均有文档更新。
- 抽检 3 份核心文档与代码一致性。
- 修复新增死链与明显失效截图/命令。
- 更新 `deprecated` 文档的替代链接。

### 每月巡检（2-4 小时）

- 统计治理指标并记录趋势（覆盖率、死链、冲突数）。
- 识别重复主题并收敛到单一 Canonical。
- 清理长期无人维护且无访问价值的 Working 文档。
- 更新目录索引，确保入口页与实际结构一致。

### 每季度审计（半天）

- 复核分层模型是否仍匹配团队组织与交付流程。
- 对历史文档进行归档批处理，减少“活文档噪音”。
- 评估术语体系一致性，消除跨团队语义漂移。

## 文档评审检查清单（增强版）

评审时建议按以下顺序检查：

1. 事实正确：与代码、配置、脚本、行为一致。
2. 结构正确：符合分层模型，位置与命名合理。
3. 引用正确：链接可达，引用对象为权威源。
4. 操作正确：步骤可执行，含输入、输出、异常分支。
5. 维护正确：含 owner、状态、更新时间、适用范围。

## 与代码仓协同规则（Docs-as-Code）

- 文档变更应与代码变更同 PR 提交（除应急补债外）。
- 影响接口/配置/部署的改动，禁止“仅代码不更新文档”。
- 大型迁移可分批提交，但每批都需保持可导航和可解释。
- 关键文档（Canonical）建议保护分支策略，避免未审合入。

## 文档分类与最小标准

### 1) 开发文档（Development Docs）

至少应包含：

- 背景与目标（为什么做）
- 范围与非目标（做什么/不做什么）
- 实现方案（模块、流程、关键决策）
- 依赖与约束（运行环境、版本、外部服务）
- 验证方式（如何确认有效）

### 2) 设计文档（Design Docs）

至少应包含：

- 用户问题与场景
- 信息架构或交互流程
- 关键状态说明（空态、加载态、错误态、成功态）
- 设计取舍（为什么选择 A 而不是 B）
- 可访问性与可理解性注意项

### 3) 日志与变更文档（Logs / Changelog）

至少应包含：

- 变更日期
- 变更摘要
- 影响范围（模块/页面/脚本）
- 风险与回滚要点（如适用）
- 验证结论

### 4) 操作与说明文档（Runbook / README / SOP）

至少应包含：

- 前置条件
- 操作步骤（可复制执行）
- 常见错误与排查方法
- 输出结果示例
- 联系方式或责任边界（可选）

## 标准工作流（必须遵守）

### Step 1: 识别文档任务类型

先判断本次请求属于：

- 新建文档
- 更新既有文档
- 文档重构（结构整理）
- 文档校验（对齐代码与现状）
- 文档归档（过期内容下线与历史留存）

### Step 2: 收集事实来源

可用来源包括：

- 当前仓库文件（代码、配置、脚本、已有文档）
- 用户明确提供的信息
- 已有决策记录（若存在）
- CI/发布输出（若能访问）
- 线上事故与问题单（若存在）

禁止做法：

- 在事实不完整时臆造“已完成”“已验证”结论
- 把猜测当成事实写入正式文档
- 复制旧文档但不校验现状

### Step 3: 输出或更新文档

输出时应做到：

- 先给结论，再给细节
- 小节可扫描（短段落、清晰标题）
- 路径、命令、文件名使用反引号标注
- 对“未完成项”明确标记 TODO/NEXT
- 对关键结论标注“适用版本/适用环境”

### Step 4: 自检（质量闸门）

提交前逐项检查：

1. 一致性：是否与代码/配置一致
2. 完整性：是否覆盖最小必要章节
3. 可执行性：步骤是否可复现
4. 可追踪性：是否记录变更时间与原因
5. 可维护性：是否避免重复和冲突表述
6. 可观测性：是否给出验证入口（日志、命令、截图点位、指标名）
7. 可版本化：是否标注版本、日期、责任人或来源

### Step 5: 交付说明

对用户反馈时至少包含：

- 修改了哪些文档文件
- 每个文件新增/调整了什么内容
- 仍存在的风险、假设或待补信息
- 是否建议同步 CI 检查项（如 markdown lint、死链检查）

## PR 级文档门禁清单（建议）

在每次 PR/变更交付时，按下列清单判断：

- 是否影响使用方式、部署方式、配置方式？
- 是否新增或修改对外行为（接口、命令、交互）？
- 是否新增风险或运维动作？
- 是否补齐验证步骤与示例输出？
- 是否更新相关索引文档（README 或 docs 入口）？

若任一项为“是”，文档更新应视为必需项，而非可选项。

## 版本策略（建议默认）

- Patch（修订）：仅修正文案错误或补充不改变行为的说明。
- Minor（增强）：新增文档章节、补充流程、扩展排障指南。
- Major（重构）：文档结构重组、术语体系调整、入口迁移。

每次 Major 变更应提供迁移说明，避免历史链接失效。

## 文风与格式约束

- 语言准确、简洁，避免口号式表述。
- 一个段落只表达一个核心点。
- 尽量用“结论 + 依据”结构。
- 引用路径、命令、环境变量时保持精确。
- 不写无依据的性能结论、安全结论、完成度结论。
- 对关键名词使用统一术语，不同文档避免同义词混用。

## 反模式清单（必须避免）

- “文档已更新”但未提供实际路径或变更点。
- 文档步骤依赖隐性前提（如环境变量已配置）却未写明。
- 变更日志只有“优化若干”这类不可追踪表述。
- README 与 docs 内容分叉，长期不一致。
- 把临时聊天结论直接当作长期规范。

## 与工程节奏配合方式

1. 每次功能变更后，优先同步以下文档：
   - 相关模块说明
   - 变更日志
   - 操作/部署说明（如受影响）
2. 每个迭代结束时，做一次“文档一致性巡检”。
3. 每月至少一次“死链与过期内容清理”。
4. 每季度执行一次文档结构审计（入口、分层、重复内容）。
5. 交接前，确保存在“当前状态 + 未完事项 + 风险清单”三件套。

- 为关键文档添加 Front Matter（owner、last_updated、status）。

## 与 `doc-updater` 的协同规则（防冲突）

为避免“多技能重复改同一文档”或“生成后无人验收”，执行以下固定分工：

1. `doc-updater` 只负责“从代码生成/刷新文档”，不做最终完成判定。
2. 本技能负责“门禁验收与治理裁决”（触发矩阵、证据、评分卡、DoD）。
3. 推荐顺序：先执行 `doc-updater`，再由本技能做一致性校验与收口。
4. 若两者结论冲突，以本技能硬门禁为准，并输出冲突说明与修复动作。
5. 任何涉及路径迁移的任务，必须由本技能执行“映射 + 修链 + 校验”闭环。

最小交接信息（`doc-updater` -> `documentation-maintainer`）：

- 扫描范围（目录与文件模式）
- 生成/更新文件清单
- 关键结论与事实来源
- 未验证项与风险假设

## 维护产物下沉（给开发 Agent 的低污染契约）

为保证开发 Agent 在日常开发中延续维护结果，维护任务完成后应同步维护：

- `docs/_meta/docs-contract.md`（短契约，10-20 行）

该文件只保留硬规则，不放长解释，建议包含：

1. 主入口：`docs/README.md`
2. Canonical 目录白名单
3. `_backup` 禁止作为默认引用目标
4. 涉及路径变更时必须更新索引并执行校验
5. 不确定时先不迁移路径，仅提交评估与映射

目标：让开发 Agent 读取最小规则即可执行，避免每次加载整份 Skill 造成上下文污染。

## 成功标准（Definition of Done）

当且仅当满足以下条件，文档任务才算完成：

- 用户能快速理解“为什么改、改了什么、如何验证”。
- 新成员可根据文档复现实操步骤。
- 文档与仓库现状一致，无明显冲突。
- 待办与风险被明确标注，不隐藏不确定性。
- 关键文档具备 owner 与最近更新时间信息。
- 至少一个文档入口可引导读者找到完整上下文。
